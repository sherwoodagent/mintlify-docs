title: "HTTP API"
description: "Read Sherwood state and prepare unsigned onchain transactions over JSON."

The HTTP API exposes read helpers and calldata encoders. State-changing endpoints return unsigned transactions. They never accept a private key or broadcast on your behalf.

## Base URLs

Choose one form and keep its path convention:

| Host | Example health URL |
| --- | --- |
| Dedicated API | `https://api.sherwood.sh/health` |
| Website equivalent | `https://www.sherwood.sh/api/v1/health` |

Do not add `/v1` after `https://api.sherwood.sh`. The dedicated host already rewrites its root to the website's `/api/v1` tree.

```bash
curl -s https://api.sherwood.sh/health
curl -s https://api.sherwood.sh/funds?chain=46630
```

<Warning>
  Always send `chain=46630` or `chainId=46630`. The machine-readable catalog can retain legacy chain records for compatibility. A catalog entry is not proof of a current public deployment.
</Warning>

## Response envelope

Successful and failed responses use a common shape:

```json
{
  "success": true,
  "data": {},
  "meta": {
    "command": "health.shallow",
    "chainId": 46630,
    "timestamp": "2026-07-16T12:00:00.000Z"
  }
}
```

On failure, `success` is `false`, `data` is omitted, and `error` describes the failure. Unsigned integers that can exceed JavaScript's safe range are serialized as decimal strings.

## Current read endpoints

All paths below are relative to `https://api.sherwood.sh`.

| Endpoint | Purpose |
| --- | --- |
| `GET /` | Machine-readable API catalog |
| `GET /health` | Service health; add `?deep=1` for RPC checks |
| `GET /chains` | Deployment registry; filter public use to chain `46630` |
| `GET /funds?chain=46630` | Active funds from the current factory |
| `GET /funds/resolve?chain=46630&vault=0x...` | Resolve a vault or fund label |
| `GET /vaults/:address?chain=46630` | Vault, asset, owner, governor, and liquidity state |
| `GET /governor?chain=46630&vault=0x...` | Parameters for one fund's governor |
| `GET /proposals?chain=46630&vault=0x...` | Proposals for one fund, newest first |
| `GET /proposals/:id?chain=46630&vault=0x...` | One vault-scoped proposal |

Proposal IDs require a vault because each fund has its own governor.

## Current prepare endpoints

Most prepare routes accept either query parameters with `GET` or a JSON body with `POST`. Routes with nested or unbounded calldata are `POST` only.

| Endpoint | Result |
| --- | --- |
| `/prepare/create-fund` | Fund creation through the deployed factory |
| `/prepare/deposit` | Approval and ERC-4626 deposit calls |
| `/prepare/redeem` | Instant ERC-4626 redemption call |
| `/prepare/request-redeem` | Lane B redemption request |
| `/prepare/approve-depositor` | Owner approval for a depositor |
| `/prepare/propose` | Proposal with execute and settlement arrays |
| `/prepare/vote` | `For`, `Against`, or `Abstain` vote |
| `/prepare/execute` | Approved proposal execution |
| `/prepare/settle` | Normal proposal settlement |
| `/prepare/cancel` and `/prepare/veto` | Allowed pre-execution controls |
| `/prepare/unstick` | Settlement with pre-committed calls |
| `/prepare/emergency-settle` | Guardian-reviewed replacement settlement calls |
| `/prepare/strategy-deploy` | Deterministic clone and atomic initialization |
| `/prepare/guardian-stake` | Guardian stake transaction |
| `/prepare/guardian-unstake` | Request, cancel, or claim unstake |
| `/prepare/guardian-delegate` | Delegation transaction |
| `/prepare/governor-set` | Bounded per-fund parameter update |

Routes for undeployed identity or attestation systems are intentionally omitted from this public surface.

## Prepare a deposit

First read the vault and confirm its asset and deposit access. The API deposit path expects the signer to hold the vault's ERC-20 asset.

```bash
curl -s 'https://api.sherwood.sh/vaults/0xVAULT?chain=46630'

curl -sX POST https://api.sherwood.sh/prepare/deposit \
  -H 'content-type: application/json' \
  -d '{
    "chainId": 46630,
    "vault": "0xVAULT",
    "receiver": "0xSIGNER",
    "amountDecimal": "0.01"
  }'
```

The response contains a `PreparedAction`:

```ts
interface PreparedAction {
  txs: Array<{
    to: `0x${string}`;
    data: `0x${string}`;
    value: `0x${string}`;
    chainId: number;
  }>;
  preconditions: Array<Record<string, unknown>>;
  description: string;
  note?: string;
}
```

Process transactions in array order and wait for each receipt before sending the next. Recheck every precondition at signing time.

## Prepare a vote

```bash
curl -sX POST https://api.sherwood.sh/prepare/vote \
  -H 'content-type: application/json' \
  -d '{
    "chainId": 46630,
    "vault": "0xVAULT",
    "proposalId": "1",
    "vote": "Against"
  }'
```

Valid vote strings are case-sensitive: `For`, `Against`, and `Abstain`.

## Error model

| HTTP status | Meaning |
| --- | --- |
| `400` | Malformed or unsupported request |
| `404` | Requested fund, vault, or proposal was not found |
| `429` | Per-IP rate limit exceeded |
| `500` | Internal server error |
| `503` | RPC or required upstream service unavailable |

Retry `503` and `429` with bounded exponential backoff. Do not retry a validation error without changing the request.

<Note>
  The current deployment reports a tripped rate limit as `500` with the error message `Rate limit exceeded — try again in a minute`. Treat that specific response as a `429` and retry with backoff.
</Note>

## Signing boundary

Before signing any returned transaction:

1. require `chainId === 46630`
2. verify every target against [deployments](/reference/deployments) or the fund's resolved contracts
3. decode approvals and governance calls
4. simulate the complete ordered batch
5. enforce your own value, slippage, and permission limits
