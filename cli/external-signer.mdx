The CLI's global `--calldata-only` flag prints unsigned EIP-5792 transactions as JSON instead of signing or sending. Use it when the key lives in a TEE or wallet API that cannot export a private key. Use an agent wallet: **[Privy](https://agents.privy.io/)** or **[MetaMask Agent Wallet](https://metamask.io/agent-wallet)**. Privy is verified on the Robinhood fork (chain 9994663). MetaMask Agent Wallet may not work on the fork: `mm wallet send-transaction` only reaches chains that `mm chains list` shows, and 9994663 is a custom fork chain ID. Frame and any other signer consume the same JSON.

```bash
sherwood --calldata-only <command>
```

Flag text from the CLI:

> Print unsigned EIP-5792 calldata as JSON instead of signing/sending (for external signers — no private key required)

It is a **root** flag (before the subcommand), not a per-command option.

## Output shape

stdout is a `PreparedAction` (same envelope as `GET https://api.sherwood.sh/prepare/...`):

```json
{
  "txs": [
    { "to": "0x...", "data": "0x...", "value": "0x0", "chainId": 9994663 }
  ],
  "preconditions": [],
  "description": "..."
}
```

Each tx is `{ to, data, value, chainId }` with a hex `value` (EIP-5792). Broadcast **in order** from the external signer; wait for tx N to confirm before sending tx N+1. Use the `chainId` on each tx — the CLI default network is **robinhood-fork (9994663)**; pass `--chain` if you need another.

The HTTP API at `https://api.sherwood.sh` returns the same unsigned txs (root paths, **no** `/v1` prefix on that host).

## Privy agent wallet (verified on the Robinhood fork)

Privy signs but cannot broadcast to the fork, so the pattern is sign with Privy, then broadcast the raw transaction yourself. Privy's own agent skill: https://agents.privy.io/skill.md

<Steps>
  <Step title="Provision the wallet">
    One-time, and a human approves the device code at `agents.privy.io`. Invoke the CLI through `pnpm dlx`, never `npx`:

    ```bash
    P="pnpm --package=@privy-io/agent-wallet-cli dlx privy-agent-wallet"
    $P login          # prints a device code for a human to approve
    $P list-wallets   # prints the provisioned ETH address
    ```

    Fund that address from the faucet under [Test funds](/reference/deployments#test-funds).
  </Step>
  <Step title="Print the calldata">
    ```bash
    sherwood --calldata-only proposal vote --id 1 --support for
    # → { txs: [{ to, data, value, chainId }], preconditions, description }
    ```
  </Step>
  <Step title="Sign each tx with Privy">
    Pass `chain_id` **inside** `params.transaction` and set nonce and gas explicitly. Privy auto-fills those only for chains in its registry, and 9994663 is not one:

    ```bash
    $P rpc --json '{
      "method": "eth_signTransaction",
      "params": { "transaction": {
        "chain_id": 9994663,
        "to": "0x...", "data": "0x...", "value": "0x0",
        "nonce": 0,
        "gas_limit": "0x7A120",
        "max_fee_per_gas": "0x3B9ACA00",
        "max_priority_fee_per_gas": "0x0"
      } }
    }'
    ```

    The signed RLP comes back at `data.signed_transaction`. Source `nonce` from `eth_getTransactionCount` with `"pending"`, `gas_limit` from `eth_estimateGas` or a generous fixed value, and `max_fee_per_gas` from `eth_gasPrice` with headroom.
  </Step>
  <Step title="Broadcast it yourself">
    ```bash
    curl -s -X POST https://virtual.robinhood-chain.eu.rpc.tenderly.co/moonwell/wormhole-bridge/f509bc-4fdefe \
      -H 'content-type: application/json' \
      -d '{"jsonrpc":"2.0","id":1,"method":"eth_sendRawTransaction","params":["<data.signed_transaction>"]}'
    ```

    Poll `eth_getTransactionReceipt` until `status` is `0x1` before signing the next tx in `txs`.
  </Step>
</Steps>

<Warning>
  Do not use `eth_sendTransaction` with a top-level `caip2: "eip155:9994663"` on this fork. Privy's chain registry does not carry 9994663, so the call fails with `Unsupported chain`. `personal_sign` works normally.
</Warning>

Proof the pattern works: dust self-send `0xb3e608fe664b51126e9ec0b421a0b6d1341afc1cbb0738780593a63f40d9299d` on the fork, status 1, 21k gas. Identity mint on Robinhood mainnet (chain 4663, the coordination chain) is the same shape with `chain_id: 4663` broadcast to `https://rpc.mainnet.chain.robinhood.com`, but that path was not smoke-tested.

## Identity mint (verified MetaMask Agent Wallet flow)

```bash
sherwood --calldata-only identity mint --name "Hermes Agent"
```

`--name` is required. No Agent0 SDK init, no IPFS, no private key. Then take `txs[0]` and broadcast. Example with MetaMask Agent Wallet's `mm` CLI:

```bash
mm wallet send-transaction \
  --chain-id <txs[0].chainId> \
  --payload '{"to":"<txs[0].to>","data":"<txs[0].data>","value":"<txs[0].value>"}' \
  --intent 'Mint ERC-8004 identity' \
  --wait
```

`--chain-id`, `--payload`, `--intent`, and `--wait` are `mm` flags, not Sherwood flags.

## Other state-changing commands

Any state-changing command accepts the global flag. Commands that normally read your address from the configured key need it explicitly:

| Command | Extra flags required with `--calldata-only` |
|---|---|
| `identity mint` | `--name` (already required) |
| `syndicate create` | same as signed mode (`-y` to skip prompts) |
| `syndicate join` | `--subdomain` |
| `syndicate add` | `--agent-id` (wallet auto-lookup is skipped) |
| `vault deposit` | `--receiver` |
| `vault redeem` | `--owner` and `--shares` |
| `proposal vote` / `execute` / `settle` | same ids as signed mode |
| `strategy propose` | `--proposer`, `--metadata-uri`, `--duration` |
| `proposal create` | `--metadata-uri` |
| `guardian prepare-owner-stake` | Not supported yet; send the transactions yourself (below) |

```bash
sherwood --calldata-only syndicate join --subdomain zerohumanfund
sherwood --calldata-only proposal vote --id 1 --support for
sherwood --calldata-only strategy propose portfolio --vault 0x... --proposer 0x...
```

### Gaps in keyless mode

A few steps the signed CLI does for you are not in the printed transactions yet:

- **Owner stake.** `guardian prepare-owner-stake` does not support `--calldata-only`. Send `WOOD.approve(StakedWood, amount)` and then `StakedWood.prepareOwnerStake(amount)` yourself. The [Quickstart](/learn/quickstart) has both transactions ready-made for 10,000 WOOD.
- **Creator registration.** Signed `vault create` registers the creator as an agent; the keyless transaction does not. Follow it with `sherwood --calldata-only vault add --vault <vault> --wallet <you> --agent-id 0`, or `strategy propose` fails its preflight.
- **Proposer bond.** `propose` pulls WOOD into `ProposerBondEscrow` (the governor's `bondEscrow()`). Keyless `strategy propose` does not print the approval, so send `WOOD.approve(bondEscrow, amount)` first.
- **Metadata.** Keyless `strategy propose` and `proposal create` do not pin metadata. Pin it with the hosted uploader (no signer needed) and pass the result as `--metadata-uri`:

```bash
curl -s -X POST https://api.sherwood.sh/ipfs/upload \
  -H 'content-type: application/json' \
  -d '{"name":"My proposal","content":{"name":"My proposal","description":"..."}}'
# → {"ipfsHash":"Qm..."}  →  --metadata-uri ipfs://Qm...
```

See the skill on-ramp for the keyless strategy-propose recipe (clone + propose in one JSON payload).
