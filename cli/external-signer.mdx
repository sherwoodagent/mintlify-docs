Sherwood agents run on a **sign-only agent wallet**: the CLI never holds the key. Every write command takes the root flag `--calldata-only` and prints the transactions; the wallet signs and broadcasts them. Use the **[MetaMask Agent Wallet](https://metamask.io/agent-wallet)** (`mm`) first; **[Privy](https://agents.privy.io/)** is the second option. Frame, a TEE, or any other signer consumes the same JSON.

```bash
sherwood --calldata-only <command>
```

Flag text from the CLI:

> Print unsigned EIP-5792 calldata as JSON instead of signing/sending (for external signers — no private key required)

It is a **root** flag (before the subcommand), not a per-command option.

## Output shape

stdout is a `PreparedAction` (same envelope as `GET https://api.sherwood.sh/prepare/...`):

```json
{
  "txs": [
    { "to": "0x...", "data": "0x...", "value": "0x0", "chainId": 4663 }
  ],
  "preconditions": [],
  "description": "...",
  "note": "..."
}
```

Each tx is `{ to, data, value, chainId }` with a hex `value` (EIP-5792). Every tx targets **Robinhood Chain (4663)**, the CLI's default and only network. Progress lines go to stderr, so stdout pipes straight into a signer.

The HTTP API at `https://api.sherwood.sh` returns the same unsigned txs (root paths, **no** `/v1` prefix on that host).

## Sign-then-broadcast loop

For each entry of `txs`, in order: show the user what it does (any tx that pays, approves, stakes or deposits needs their yes), send it from the wallet with that entry's `chainId` (4663), wait for the receipt with `status: 1`, then move to the next. If one reverts, stop: do not send the rest.

```bash
OUT=$(sherwood --calldata-only guardian prepare-owner-stake 10000)
echo "$OUT" | jq -c '.txs[]' | while read -r tx; do
  # MetaMask (below) or Privy (below); wait for the receipt before the next tx
  mm wallet send-transaction --chain-id "$(echo "$tx" | jq -r .chainId)" \
    --payload "$(echo "$tx" | jq -c '{to,data,value}')" \
    --intent "$(echo "$OUT" | jq -r .description)" --wait || break
done
```

## MetaMask Agent Wallet (first choice)

```bash
npm i -g @metamask/agent-wallet@latest
mm login                 # prints a device code; a human approves it once
mm chains list           # needs mm login; check that it shows 4663 (Robinhood Chain); if it does not, use Privy below
mm wallet send-transaction --chain-id 4663 \
  --payload '{"to":"<txs[i].to>","data":"<txs[i].data>","value":"<txs[i].value>"}' \
  --intent '<what this tx does>' --wait
```

`--chain-id`, `--payload`, `--intent` and `--wait` are `mm` flags, not Sherwood flags.

Signing without a transaction (the CLI's two-step logins):

- **personal_sign (EIP-191)** for `sources login` and `chat --join-cohort`: `mm wallet sign-message --message '<text>' --chain-id 4663`. Sign the exact text the CLI printed.
- **EIP-712 typed data** for `research` (x402): `mm wallet sign-typed-data --chain-id 8453 --payload '<typed_data JSON>'`. Pass the `typed_data` object the CLI printed, unchanged; `--chain-id 8453` because the payment is USDC on Base.

These verbs are from `@metamask/agent-wallet` 7.0.0 `--help`.

## Privy agent wallet (second choice)

Invoke Privy's CLI via `pnpm dlx`, never `npx` (Privy's own instruction, https://agents.privy.io/skill.md):

```bash
P="pnpm --package=@privy-io/agent-wallet-cli dlx privy-agent-wallet"
$P login          # one-time: a human approves a device code at agents.privy.io
$P list-wallets   # prints the provisioned ETH address
```

Broadcasting has two branches. Use the first if Privy's chain registry carries 4663; otherwise the second. Try the first with a harmless tx (a 0-value self-send) before you rely on it.

    ```bash
    $P rpc --json '{"method":"eth_sendTransaction","caip2":"eip155:4663",
      "params":{"transaction":{"to":"<txs[i].to>","data":"<txs[i].data>","value":"<txs[i].value>"}}}'
    # → "Unsupported chain" means 4663 is not in Privy's registry: use B
    ```
  </Tab>
  <Tab title="B. Privy signs, you broadcast">
    ```bash
    $P rpc --json '{"method":"eth_signTransaction","params":{"transaction":{
      "chain_id":4663,"to":"<txs[i].to>","data":"<txs[i].data>","value":"<txs[i].value>","nonce":<n>,
      "gas_limit":"<hex>","max_fee_per_gas":"<hex>","max_priority_fee_per_gas":"<hex>"}}}'
    # → data.signed_transaction (signed RLP)
    curl -s -X POST https://rpc.mainnet.chain.robinhood.com -H 'content-type: application/json' \
      -d '{"jsonrpc":"2.0","id":1,"method":"eth_sendRawTransaction","params":["<data.signed_transaction>"]}'
    ```

    Put `chain_id` **inside** `params.transaction` and set nonce and gas explicitly: `nonce` from `eth_getTransactionCount(<wallet>, "pending")`, `gas_limit` from `eth_estimateGas` (or a generous fixed value), `max_fee_per_gas` from `eth_gasPrice` with headroom. Poll `eth_getTransactionReceipt` for `status: 0x1` before the next tx.
  </Tab>

Signing without a transaction: `personal_sign` for `sources login` / `chat --join-cohort`, `eth_signTypedData_v4` for `research` (x402), both through `$P rpc`:

```bash
$P rpc --json '{"method":"personal_sign","params":{"message":"<message>","encoding":"utf-8"}}'
$P rpc --json '{"method":"eth_signTypedData_v4","params":{"typed_data":<typed_data>}}'
```

## Two-step commands (sign, then complete)

Three commands need a signature that is not a transaction. Each prints what to sign, and a second call with `--signature` completes it.

### Data feeds: `sources login`

```bash
sherwood sources login --address <agent wallet> --json   # → message
#   personal_sign the exact message within 10 min:
#     MetaMask: mm wallet sign-message --message '<text>' --chain-id 4663
#     Privy:    $P rpc --json '{"method":"personal_sign","params":{"message":"<message>","encoding":"utf-8"}}'
sherwood sources login --signature 0x…
```

The token lasts **1 hour** with no refresh: re-login hourly, or on the first `401`. `401` = log in again; `403` = the wallet is not approved, tell the vault owner and never retry with another wallet. See [Sources commands](/cli/sources-commands).

### Cohort chat: `chat --join-cohort`

```bash
sherwood chat --join-cohort --address <agent wallet> --json > /tmp/join.log 2>&1 &   # step 1 stays running and waits (default 600s, --timeout <s>)
jq -r .xmtp_signature_request.message /tmp/join.log
#   personal_sign (EIP-191) that exact multi-line text ("XMTP : Authenticate to inbox …") with the agent wallet
#   (MetaMask: mm wallet sign-message --message '<text>' --chain-id 4663; Privy: $P rpc personal_sign), then:
sherwood chat --join-cohort --signature 0x…   # step 2: hands it to step 1, prints the join result (status: pending)
```

See [XMTP](/reference/integrations/xmtp).

### Research: x402 payment

Messari and Nansen are paid per call via **x402** in **USDC on Base (chain 8453)**, not from the vault and not on 4663. x402 signs EIP-712 typed data (EIP-3009 `TransferWithAuthorization` on Base USDC), so the wallet must support `eth_signTypedData_v4`. Privy does (`$P rpc`); the MetaMask Agent Wallet does through `mm wallet sign-typed-data --chain-id 8453 --payload '<typed_data JSON>'`. Ask the owner before every spend.

```bash
# Step 1: confirms the cost, sends the request, catches the 402, prints the typed data, then waits (default 600s)
sherwood research token TSLA --provider messari --address <agent wallet> --yes --json > /tmp/x402.log 2>&1 &
jq '.x402_signature_request' /tmp/x402.log
#   { wallet, provider, cost_usdc, chain_id: 8453, typed_data: {domain,types,primaryType,message}, deadline }
#   also written to ~/.sherwood/x402-signing/<wallet, lowercase>.request.json
#   Sign typed_data unchanged, before deadline:
#     MetaMask: mm wallet sign-typed-data --chain-id 8453 --payload '<typed_data JSON>'
#     Privy:    $P rpc --json '{"method":"eth_signTypedData_v4","params":{"typed_data":<typed_data>}}'
# Step 2: hands the signature to step 1, which pays, retries and prints the result
sherwood research complete --signature 0x… [--address <agent wallet>]
```

Run step 1 with `--yes` only after the owner said yes to that cost. Step 2 exits 1 with the reason when no step 1 is waiting or the deadline has passed: start step 1 again.

**Deadlines.** The provider sets the payment window (`maxTimeoutSeconds` in its 402): Messari 60 s, Nansen 300 s. With Messari that leaves about 57 s to sign and run step 2, so have the signer ready first. Nansen is the safer provider for sign-only wallets.

**Two payments.** A query that needs two paid calls (Messari `market`) makes step 2 print the next `x402_signature_request` and exit 0: sign it and run `sherwood research complete` again. Step 1 sends the payment in the x402 v2 `PAYMENT-SIGNATURE` header.

## Commands that need an address

Any state-changing command accepts the global flag. Commands that normally read your address from the configured key need it explicitly:

| Command | Extra flags required with `--calldata-only` |
|---|---|
| `identity mint` | `--name` (already required) |
| `guardian prepare-owner-stake` | none; prints the WOOD approval and `prepareOwnerStake` |
| `vault create` | `--creator <wallet>` (enables the bond, fee and identity checks), `-y` |
| `vault add` | `--agent-id` (wallet auto-lookup is skipped) |
| `vault join` | `--subdomain` |
| `vault deposit` | `--receiver` |
| `vault redeem` | `--owner` and `--shares` |
| `proposal vote` / `execute` / `settle` / `reclaim-bond` | same ids as signed mode |
| `strategy propose` | `--proposer`, `--duration`, and `--metadata-uri` (or `--name` / `--description`) |
| `proposal create` | `--proposer` is optional: it enables the proposer-bond balance and allowance check |
| `sources login`, `chat --join-cohort`, `research` | `--address` (two-step, above) |

### What the printed transactions cover

Keyless mode prints everything the signed CLI sends:

- **Owner stake.** `guardian prepare-owner-stake` prints the WOOD approval to `StakedWood`, then `prepareOwnerStake`.
- **Proposer bond.** `strategy propose` and `proposal create` put the WOOD approval to the governor's `bondEscrow()` first when it is needed. With a proposer address, the CLI checks the wallet holds the quoted bond (`InsufficientProposerBondWood`) and skips the approval when the allowance already covers it.
- **Metadata.** Without `--metadata-uri`, both commands pin `--name` / `--description` through the hosted uploader, which needs no signer.

One step is still yours: signed `vault create` registers the creator as an agent, and the keyless transaction cannot, because the vault address is not known until it confirms. Follow it with `sherwood vault info <subdomain>`, then `sherwood --calldata-only vault add --vault <vault> --wallet <creator> --agent-id <id>`, or keyless `strategy propose` refuses (`not a registered agent`). The printed `note` names both commands.

The full box flow, in order, is in the [Quickstart](/learn/quickstart).
